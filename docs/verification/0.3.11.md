# 0.3.11 재시작 후 라이브 검증

2026-09-04, 배포 커밋 `f25ee79`. Claude Code 재시작 후 설치본이 실제로 0.3.11로 갱신됐는지 확인하고, 이번 버전에서 추가된 두 규칙(fight-audit 대상 태그, fight-clarify 컨텍스트 상한)이 실제 호출에서 동작하는지, 그리고 기존 시나리오 1–3이 여전히 기대대로 동작하는지 재확인했다.

## 방법과 범위

Claude Code에서 `Agent` 툴로 제안자→감사자(fight-audit, 순차) 또는 해석자 2회 병렬(fight-clarify)을 실제로 호출했다. 모델은 스킬 계약대로 fight-audit 제안자 `sonnet`/감사자 `opus`, fight-clarify 두 해석자 `sonnet`이다. 시나리오 2·3은 이 저장소를 대상으로 한 실제 지시를 썼고, 시나리오 1은 0.3.10 방법론과 동일하게 저장소 밖 가상 코드를 입력으로 썼다(호출 계약 검증이 목적이며 실제 파일 수정은 하지 않음). Codex 쪽은 이 세션에 Codex CLI가 없어 재검증하지 않았다.

## 설치본 확인

`installed_plugins.json`의 `fight@fight` 항목: `version: 0.3.11`, `installPath: ...\cache\fight\fight\0.3.11`, `gitCommitSha: f25ee79...`. 재시작 후 0.3.11이 실제로 로드됨을 확인했다.

시나리오 1의 결과는 0.3.10 이전 기록("Claude Code: 통과")과 다르다. 이번 재실행은 지시 자체가 아니라 제안자 출력의 인용 조작·범위 오판을 감사자가 잡아낸 사례이며, 프로토콜이 매번 "이의 없음"을 보장하지 않고 실제로 결함이 있으면 통과시키지 않음을 보여준다. 반례 없음(같은 가상 입력 반복 실행은 하지 않았다).

## 0.3.11 신규 규칙의 실동작 확인

- **fight-audit 대상 태그**: 시나리오 2 재실행에서 `[대상: 지시]`·`[대상: 제안안]`뿐 아니라 두 태그가 동시에 붙는 경우(`실패 모드 — BLOCK [대상: 지시][대상: 제안안]`)까지 실제로 관측했다.
- **fight-clarify 컨텍스트 상한**: 스킬 호출 시 출력된 `SKILL.md` 본문에 "해석자 컨텍스트 수집과 상한" 절이 포함돼 있음을 확인했다(fight-audit 절 참조, 숫자 재복제 없음).

## 한계

미검증 사례에서 드러나듯, 시나리오 1의 가상 입력은 실제 호출 그래프나 CI 설정이 없어 그 부분의 검증은 원천적으로 불가능했다 — 이는 프로토콜 결함이 아니라 가상 입력의 한계다. Codex 쪽 재검증은 별도 세션이 필요하며 이 기록에 포함하지 않았다.
