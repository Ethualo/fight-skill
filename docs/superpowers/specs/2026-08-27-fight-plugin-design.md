# fight — 적대적 검증 플러그인 설계

작성일: 2026-08-27
상태: 설계 승인됨, 구현 계획 대기

## 1. 목적

유저의 지시나 제안에 대해 컨텍스트가 격리된 두 서브에이전트를 붙여, 메인 스레드 단독으로는
나오지 않는 검증과 대안을 얻는다. 세 가지 문제를 겨냥한다.

1. **동조 방지** — 메인 스레드가 유저 제안에 무비판적으로 동의하는 경향
2. **모호한 지시 구체화** — 유저 본인도 아직 언어화하지 못한 요구를 실물 대안으로 드러내기
3. **품질 최적화** — 채택안의 리스크·비용·대안 검토

### 핵심 가정

이 설계가 성립하는 근거는 "토론"이 아니라 **컨텍스트 격리**다. 서브에이전트는 메인 스레드의
추론 캐시를 공유하지 않으므로, 메인이 이미 유창하게 전개한 논리에 끌려가지 않는다. 또한
"유저가 X를 원한다"는 신호를 특정 에이전트에게만 선택적으로 숨길 수 있는데, 이는 단일
컨텍스트에서는 불가능하다.

### 비목표

- 합의될 때까지 라운드를 반복하는 무제한 토론. LLM끼리는 쉽게 서로 양보해 가짜 합의에 도달한다.
- 사소한 작업에 대한 자동 발동. 비용이 가치를 넘는다.
- `fight-clarify` 결과를 `fight-audit`으로 자동 연결. 필요하면 유저가 이어서 호출한다.

## 2. 구조

플러그인 하나, 스킬 두 개, 파일 다섯 개.

```
fight/
  .claude-plugin/plugin.json
  hooks/hooks.json                 # SessionStart 규칙 주입
  skills/fight-audit/SKILL.md      # 동조 방지 + 품질
  skills/fight-clarify/SKILL.md    # 모호한 지시 구체화
  CLAUDE.md
```

### 결정: 커스텀 에이전트 정의 파일을 만들지 않는다

역할 프롬프트는 각 SKILL.md 안에 인라인 템플릿으로 두고, `Agent` 툴의 `general-purpose`로
띄운다. 매 호출마다 유저 지시와 컨텍스트를 끼워 넣어야 하므로 어차피 템플릿이 필요하고,
별도 에이전트 파일은 그 위에 얹는 껍데기가 된다.

### 결정: 판정은 메인 스레드가 한다

제3의 심판 에이전트를 두지 않는다.

- 서브에이전트 호출을 스킬당 1회 절약한다 (스킬당 총 2회).
- 메인 스레드만 대화 히스토리와 코드베이스 컨텍스트를 가진다. 심판에게는 그것을 다시 요약해
  넘겨야 한다.
- 편향 우려는 이미 해소되어 있다. 격리는 토론 단계에서 일어났고, 메인은 독립적으로 생성된
  보고서를 받는다. 메인이 유저에게 동조하려 해도 감사자 보고서가 텍스트로 남아 있어 무시가
  눈에 보인다.
- 메인이 판정해야 곧바로 `AskUserQuestion`으로 쟁점을 유저에게 올릴 수 있다.

### 결정: 1라운드 고정

재반박 라운드는 판정을 거의 바꾸지 않으면서 비용을 두 배로 만든다. 가변 라운드는 비용 예측을
불가능하게 한다.

### 결정: 역할 구조 — `fight-audit`은 비대칭, `fight-clarify`는 대칭

두 스킬의 구조가 다른 이유는 편의가 아니라 **잡으려는 오류의 종류가 다르기 때문**이다.

**대칭 구조는 분산(variance)을 잡는다.** 두 에이전트가 같은 질문을 받고 각자 답한 뒤 서로
비판한다. 두 답이 갈리는 지점이 모델이 흔들리는 지점이고, 겹치는 지점은 신뢰의 증거가 된다.

대칭의 치명적 한계는 두 에이전트가 **같은 방향으로** 틀릴 때 이를 잡지 못한다는 것이다.
오히려 그것을 합의로 읽어 신뢰도를 올린다. 동조는 정확히 이 종류의 오류다. 같은 모델
두 개는 같은 지시에 같은 방향으로 아부한다. 따라서 **같은 모델로 대칭을 구성하면 동조
방지가 원리적으로 성립하지 않는다.** `agent-arena`가 이종 모델(Codex 대 Claude)을 쓰는
이유가 이것이며, 그 구조에서는 선택이 아니라 필수다 (8절 참조).

**비대칭 구조는 편향(bias)을 잡는다.** 역할이 다르고 입력도 출력 형식도 다르다. 하나는
생산하고 하나는 검증한다.

이 설계는 이종 모델을 쓰지 않는다. 외부 CLI 설치·인증 의존이 생겨 자체 완결성이 깨지기
때문이다. 대신 **역할 비대칭을 모델 다양성의 대체재로 쓴다.** 프롬프트로 서로 다른
목적함수를 심어 인공적 이질성을 만든다. 감사자의 목적함수는 "좋은 답 찾기"가 아니라
"이 답이 틀릴 이유 찾기"이므로, 같은 모델이어도 유저 제안에 동조할 유인이 없다.

부수 효과가 하나 더 있다. 감사자는 그 안을 자기가 만들지 않았으므로 애착이 없다. 대칭
구조에서는 각자 자기 답을 방어하느라 상대의 지적을 깎으려는 압력이 생긴다.

| | 대칭 | 비대칭 |
|---|---|---|
| 격리 대상 | 답 (독립 후보 2개) | 생산과 검증 |
| 잡는 오류 | 분산 | 편향 |
| 같은 모델로 성립하는가 | 아니오 | 예 |
| 출력 | 답 2개, 합치거나 고름 | 안 1개 + 지적 목록 |
| 판정 난이도 | 높음. "A 대 B 대 A+B" 얕은 추론에 빠지기 쉬움 | 낮음. "어느 지적을 받아들일까" |
| 고유 실패 모드 | 두 답이 실은 같음 = 낭비 | 낼 것이 없는데 내야 함 = 억지 반대 |

구조를 고르면 그 구조의 실패 모드가 딸려온다. 비대칭의 실패 모드가 억지 반대이며,
3절의 6축 근거 강제와 실패 시나리오 게이트는 정확히 그 하나를 막기 위한 장치다.

`fight-clarify`가 대칭인 이유는 목적이 편향 잡기가 아니라 **해석 공간 벌리기**이기
때문이다. 모호한 지시에는 분산이 실제로 존재한다 — 여러 해석을 진짜로 허용한다. 대칭이
잡는 것이 분산이므로 여기서는 맞는 도구다. 나아가 극단을 배정해 분산을 인공적으로 키운다.
"강제 분기 대칭"이라 부를 수 있다.

## 3. 스킬 A — `fight-audit`

동조 방지와 품질 최적화. 서브에이전트 2회 **순차** 호출. 감사자가 제안자의 안을 봐야 실제
검증이 성립하므로 병렬로 돌리지 않는다.

### A-1. 제안자

**받는 것**: 유저 지시 원문, 관련 코드 컨텍스트

**받지 않는 것**: 메인 스레드가 이미 낸 의견, 유저의 선호 뉘앙스 (앵커링 제거)

**산출물**: 구체적 구현안. 지시가 비워둔 부분은 해석을 확정하되 `[가정]` 태그를 붙인다.
근거가 있는 가정과 그냥 메운 가정을 구분해 표시한다.

### A-2. 감사자

**받는 것**: 유저 지시 원문, 제안자의 안

**원칙**: 탐색은 최대한, 보고는 증거가 있는 것만.

**공격 축** — 여섯 개 모두 필수. 축마다 판정과 근거를 출력한다. 건너뛸 수 없다.

| 축 | 검증 내용 |
|---|---|
| 전제 | 지시가 참이라 가정한 사실이 실제로 참인가. 코드를 열어 확인한다 |
| 문제 정의 | 이것이 진짜 문제인가, 증상만 건드리는가 |
| 대안 | 더 적은 비용으로 같은 목표에 도달하는 길이 있는가 |
| 비용 | 유지보수·성능·복잡도 대가 |
| 실패 모드 | 엣지케이스, 에러 경로, 동시성 |
| 되돌리기 | 틀렸을 때의 원복 비용 |

**순서**: 유저 지시 자체를 먼저 검증하고, 그다음 제안자의 안을 검증한다. 동조 방지의 실체는
앞부분이다.

**억지 반대 차단** — 이 설계에서 가장 중요한 장치다.

1. 동의를 반대보다 비싸게 만든다. 축 하나를 "통과"로 넘기려면 무엇을 어떻게 확인했는지
   근거를 써야 한다. 빈칸으로 넘기는 것이 불가능하므로 게으른 동조가 게으른 반대보다
   어려워진다. "최대한 반박점을 찾아라"라는 지시보다 강한 압력이다. 지시는 무시할 수 있어도
   빈칸은 무시할 수 없다.
2. 모든 지적에 구체적 실패 시나리오를 요구한다. 입력과 상태를 명시하고, 그 결과 무엇이
   잘못되는지 쓴다. 쓰지 못하면 그 지적은 폐기한다. 지어낸 반대는 여기서 걸러진다.
   "확장성이 우려됩니다" 같은 서술은 자동 탈락한다.

**심각도**: `BLOCK` / `WARN` / `NOTE`. 사용자의 기존 `code-review.md` 규칙과 정렬한다.

**여섯 축이 모두 통과하면 "이의 없음"으로 끝낸다.** 빈 출력이 아니다. 축마다 근거가 필수이므로
유저는 "이의 없음"과 함께 무엇을 어떻게 확인했는지 여섯 줄을 받는다. 그 여섯 줄이 안심할
근거이며, 그것이 원래 목적이다.

> 설계 과정에서 "여섯 축 통과 시 조건부 반박 하나를 강제"하는 안을 검토했으나 폐기했다.
> 미래 조건 변화 예측은 실패 시나리오 게이트를 통과하지 못할 종류인데 게이트 밖에 두어
> 통과시키는 셈이 되고, 미래 리스크는 이미 `되돌리기` 축이 다룬다. 현재 안이 의존하는 전제는
> 제안자의 `[가정]` 태그와 `전제` 축이 이미 잡는다.

### A-3. 메인 판정

- 제안자와 감사자가 합의한 부분은 조용히 확정한다.
- 감사자의 `BLOCK`과 제안자의 근거가 충돌하면 `AskUserQuestion`으로 유저에게 올린다.
- 제안자의 근거 없는 `[가정]`은 `AskUserQuestion`으로 유저에게 올린다.
- 출력은 단일 권장안 하나와 미해결 쟁점 선택지다.

## 4. 스킬 B — `fight-clarify`

모호한 지시 구체화. 서브에이전트 2회 **병렬** 호출. 목적이 반박이 아니라 해석 공간을 벌리는
것이므로 서로 검증하지 않는다.

### B-1. 애매함 축 선정

메인 스레드가 지시에서 가장 큰 애매함 축 하나를 뽑아 양극단을 정한다. 메인만 대화 히스토리를
가지므로 유저가 무엇을 정하지 않았는지 가장 잘 안다.

```
"로그인 개선해줘"  축=범위   A=최소(기존 폼 UX만)        B=최대(인증 방식 재설계)
"캐시 추가해줘"    축=계층   A=앱 레벨 메모이제이션      B=인프라 레벨 Redis
```

`AskUserQuestion` 경유로 진입한 경우 (5절) 이 단계는 생략한다. 메인이 물으려던 질문이 곧
애매함 축이다.

### B-2. 병렬 dispatch

각 에이전트는 배정된 극단으로 해석을 확정하고 구체안을 낸다. 자기 축 밖의 애매함에는
`[가정]` 태그를 붙인다.

### B-3. 메인 비교

- **두 안이 일치하는 부분**은 지시가 실제로 명확했던 지점이다. 조용히 확정하고 묻지 않는다.
  질문 공세를 막는 핵심 장치다.
- **갈린 부분**이 명세 공백이다. `AskUserQuestion`으로 올린다.
- 유저 선택 후 메인이 확정된 지시문을 재작성해 출력하고 스킬을 종료한다.

**축을 잘못 뽑은 경우**: 두 안이 비슷하게 나온다. 메인이 이를 감지해 유저에게 직접 묻는다.
별도 분기 로직 없이 자동으로 처리된다.

## 5. 발동

### `fight-audit`

슬래시 커맨드 및 스킬 `description` 자동 매칭. description에 사소한 작업에는 쓰지 말라는
조건을 명시한다.

### `fight-clarify`

위 경로에 더해, `AskUserQuestion` 선택지를 통한 진입을 주 경로로 삼는다.

메인이 `AskUserQuestion`을 호출하는 조건과 `fight-clarify`가 필요한 조건은 같다. 둘 다
"메인이 모호함을 감지했으나 스스로 정하지 못함"이다. 차이는 유저가 답을 아느냐뿐이며, 모를
때가 바로 이 스킬이 필요한 순간이다.

플러그인은 `SessionStart` 훅으로 다음 규칙을 주입한다.

```
AskUserQuestion 호출 시, 유저가 답을 모를 수 있는 설계·해석 질문이면
마지막 옵션으로 추가: "모르겠음 — 양극단 두 안 만들어서 보여줘"
선택 시 fight-clarify 스킬을 호출하고, 그 질문을 애매함 축으로 사용한다.
```

`UserPromptSubmit`이 아니라 `SessionStart`를 쓰는 이유는 세션당 1회만 실행되기 때문이다.
`UserPromptSubmit`은 매 턴 토큰을 소비한다.

**이 경로의 장점**

- 트리거 문제를 해결한다. description 자동 매칭은 신뢰도가 낮고, 슬래시 커맨드는 유저가
  필요성을 먼저 알아야 한다. 이 방식은 모호함이 이미 감지된 지점에 정확히 붙는다.
- 비용 게이트로도 최선이다. 유저가 직접 발동 여부를 고른다.
- 애매함 축 선정 단계가 불필요해진다.

**감수하는 비용**: 질문이 두 번 돈다. 두 번째 질문은 추상 선택지가 아니라 구축된 두 안을
놓고 묻는 것이므로 값어치가 있다고 판단한다.

`fight-audit`에는 이 훅을 적용하지 않는다. 대응하는 자연 게이트가 없다.

## 6. 비용

| 스킬 | 서브에이전트 호출 | 실행 방식 |
|---|---|---|
| `fight-audit` | 2 | 순차 |
| `fight-clarify` | 2 | 병렬 |

판정은 메인 스레드가 수행하므로 추가 호출이 없다.

## 7. 테스트

스킬은 마크다운 지시문이며 실행 가능한 로직을 포함하지 않는다. 단위 테스트 대상이 아니다.
검증은 실제 호출로 한다. 구현 계획 단계에서 최소 세 개의 시나리오를 정의한다.

1. 명백히 타당한 지시 — 감사자가 억지 반대를 만들어내지 않고 "이의 없음"과 근거 여섯 줄을
   반환하는지 확인한다.
2. 실제 결함이 있는 지시 — 감사자가 구체적 실패 시나리오와 함께 `BLOCK`을 내는지 확인한다.
3. 모호한 지시 — `fight-clarify`의 두 안이 실제로 갈리고, 일치 부분은 유저에게 묻지 않는지
   확인한다.

### `agent-arena`와의 차이

| | `agent-arena` | 이 설계 |
|---|---|---|
| 격리 수단 | 이종 모델. 외부 CLI 설치·인증 필요 | 동일 모델 서브에이전트 컨텍스트 격리. 자체 완결 |
| 역할 | 대칭. 둘 다 같은 질문에 답한 뒤 상호 비판 | 비대칭. 제안자 대 6축 감사자 |
| 억지 반대 방지 | 없음 | 실패 시나리오 게이트 + 축별 근거 강제 |
| 수렴 | dissent 보존, 수렴하지 않음 | 단일 권장안 + 유저가 쟁점 선택 |
| 모호 지시 구체화 | 없음 | `fight-clarify` |
| 발동 | 수동 | `AskUserQuestion` 선택지 |
| 파이프라인 | 7단계 | 1라운드 2호출 |

### 채택하지 않은 것

`agent-arena`의 evidence ledger와 claim extraction은 이 설계의 실패 시나리오 게이트와
목적이 같으나 훨씬 무겁다. 가벼운 쪽을 유지한다.

### 검토했으나 변경이 불필요했던 지적

`agent-arena`의 원칙은 "독립 생성 먼저, 토론 나중"인데, `fight-audit`은 순차 실행이므로
감사자가 제안자의 프레임에 갇힐 위험이 있다. 이는 이미 대비되어 있다. 감사자는 제안자의
안을 보기 전에 유저 지시부터 검증하며, 6축 중 `문제 정의`와 `대안`이 프레임 탈출을 강제한다.

## 9. 미결 사항

- 스킬 이름 최종 확정 (`fight-audit` / `fight-clarify`).
- 슬래시 커맨드 이름.
- 제안자에게 넘길 코드 컨텍스트의 수집 범위와 상한.
