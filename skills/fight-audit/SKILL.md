# fight-audit

두 서브에이전트로 유저 지시를 적대적으로 검증한다. **순차** 2회 호출. 판정은 메인 스레드가 한다.

감사자가 제안자의 안을 봐야 검증이 성립하므로 병렬로 돌리지 않는다.

이 스킬은 Claude Code와 Codex 양쪽에서 동작한다. 프로토콜(프롬프트, 축, 판정 규칙)은 플랫폼과 무관하게 동일하고, **호출 계약만** 아래처럼 플랫폼별로 다르다.

이 문서는 실행 오케스트레이터가 아니라 호스트 에이전트가 따를 프롬프트 프로토콜이다. 호출 수·순서·병렬성·모델 선택을 플러그인 파일이 자동 검증하거나 강제하지는 않는다.

## 공통 규칙

- 서브에이전트는 파일을 직접 수정하지 않는다. 조사와 제안만 한다.
- 외부 provider·CLI·MCP를 호출하지 않는다.
- 메인의 기존 의견과 유저 선호에 대한 인상은 제안자에게 주지 않는다. 앵커링 제거가 이 호출의 목적이다.
- 이는 메인이 전달할 텍스트를 선별하는 규칙이다. 플러그인이 의견·선호를 자동 탐지·제거하는 기능은 없다.
- 두 서브에이전트 결과 모두 올 때까지 기다린다. 반복 polling은 피한다.

## 제안자 컨텍스트 수집과 상한

- 컨텍스트는 `직접 대상 파일 → 직접 계약·설정 → 직접 호출자·소비자·테스트` 순서로 수집한다.
- 전체 저장소, git 이력, handoff, 관련 없는 역사 문서와 파일은 넘기지 않는다.
- 제안자에게 넣는 컨텍스트 블록은 최대 저장소 파일 8개, 선택한 발췌의 UTF-8 24,576 bytes다. 유저 지시 원문·이 스킬의 고정 프롬프트·에이전트 출력은 이 한도에서 제외한다.
- 한도를 넘으면 우선순위가 낮은 파일을 경로와 생략 사유만 남기고 줄인다. 한도를 조용히 초과하지 않는다.

## 1단계 — 제안자 호출

**Claude Code:** `Agent` 툴. `subagent_type: general-purpose`, `model: sonnet`, `run_in_background: false`.

**Codex:** subagent spawn 도구. `model: gpt-5.6-terra`, reasoning effort `xhigh`, `fork_context: false`. 지정 모델을 쓸 수 없으면 다른 모델로 조용히 대체하지 말고 유저에게 중단 사유를 알린다.

모델 지정은 호스트에 대한 요청이다. 조직 정책·모델 가용성으로 대체되거나 요청값을 쓸 수 없으면, 메인은 실제 설정을 밝히고 이 프로토콜 호출을 중단한다. 플러그인만으로 대체를 감지·차단할 수는 없다.

프롬프트 템플릿. 중괄호 부분을 채워 쓴다.

## 2단계 — 감사자 호출

제안자 결과를 받은 뒤 호출한다.

**Claude Code:** `Agent` 툴. `subagent_type: general-purpose`, `model: opus`, `run_in_background: false`. 두 호출 모두 `model`을 명시한다. 생략하면 부모 세션 모델을 상속하므로, Sonnet 세션에서 부르면 감사자가 조용히 Sonnet이 된다. 출력 형식은 그대로라 열화를 알아챌 방법이 없다. 감사자는 보고 규칙의 근거·실패 시나리오를 지어내지 않고 실제로 확인해야 하므로 상위모델로 고정한다. 제안자는 틀려도 감사자가 잡으므로 고정하지 않아도 된다.

**Codex:** subagent spawn 도구. `model: gpt-5.6-sol`, reasoning effort `medium`, `fork_context: false`. 모델 서열은 `sol` > `terra` > `luna` — 감사자에게 제안자(`terra`)보다 상위 모델을 쓰는 이유는 Claude Code의 opus/sonnet과 동일하다: 같은 모델은 자기 오류를 못 잡으므로 모델 티어 자체를 다르게 가져가야 이질성이 생긴다. reasoning effort는 `low`/`medium`/`high`/`xhigh`/`max`/`ultra` 6단계. effort를 `medium`으로 낮춘 것은 비용 절감 실험이다 — 벤더 가이드는 설계·보안급 판단에 `sol`+`max`를 권장하지만, 검증 목적상 필요한 건 "제안자와 다른 모델"이지 "최고 effort"가 아닐 수 있어 실측으로 확인 중이다. 라이브 검증에서 감사자가 근거·실패 시나리오 기준을 여전히 만족하는지 확인되면 `medium` 유지, 부실해지면 `xhigh`나 `max`로 올린다.

## 순서
먼저 유저 지시 자체를 검증하고, 그 다음 제안자의 안을 검증한다.
제안자가 세운 프레임 안에 갇히지 마라.
지적이 유저 지시 자체의 결함이면 `[대상: 지시]`, 제안자가 고른 구현 방법의 결함이면 `[대상: 제안안]`을 붙인다.
둘 다 해당하면 둘 다 붙인다. `BLOCK`/`WARN`/`NOTE`에만 표기하고 `통과`/`미검증`에는 붙이지 않는다.
태그 누락은 `[대상: 지시]`로 간주해 지시 재검증이 필요한 것으로 취급한다.

## 공격 축 — 여섯 개 모두 필수. 하나도 건너뛸 수 없다.
| 축 | 검증 |
|---|---|
| 전제 | 지시가 참이라 가정한 사실이 실제로 참인가. 코드를 열어 확인한다 |
| 문제 정의 | 이것이 진짜 문제인가, 증상만 건드리는가 |
| 대안 | 더 적은 비용으로 같은 목표에 도달하는 길이 있는가 |
| 비용 | 유지보수·성능·복잡도 대가 |
| 실패 모드 | 엣지케이스, 에러 경로, 동시성 |
| 되돌리기 | 틀렸을 때 원복 비용 |

## 보고 규칙
- 축마다 판정을 낸다. 판정은 `BLOCK` / `WARN` / `NOTE` / `통과` / `미검증` 중 하나다.
- `통과`로 넘기려면 무엇을 어떻게 확인했는지 근거를 쓴다. 파일 경로와 줄 번호, 실행한 명령, 확인한 함수명 중 하나를 반드시 명시한다. "문제 없음"처럼 확인 대상을 특정하지 않는 서술은 통과로 인정하지 않는다. 빈칸으로 넘기는 것은 금지다.
- 접근 거부·자료 누락·실행 환경 부재로 확인할 수 없으면 `미검증`으로 남긴다. 확인 대상, 시도한 파일·명령과 결과, 부족한 증거를 쓴다. 확인하지 않은 사실을 통과나 결함으로 꾸미지 않는다.
- `BLOCK`·`WARN`·`NOTE` 지적에는 구체적 실패 시나리오를 붙인다. 입력과 상태를 명시하고, 그 결과 무엇이 잘못되는지 쓴다.
- 실패 시나리오를 쓰지 못하는 지적은 폐기한다. 출력하지 마라. 단, `미검증`은 결함 지적이 아니므로 제품 실패 시나리오 없이도 보존한다.
  "확장성이 우려된다", "유지보수가 어려워질 수 있다" 같은 서술이 폐기 대상이다.
- 여섯 축이 모두 통과면 "이의 없음"으로 끝낸다. 억지로 지적을 만들지 마라.
  근거 여섯 줄이 곧 결과물이다.
- 파일은 수정하지 않는다.

## 출력 형식
### 축별 판정
- 전제 — {BLOCK|WARN|NOTE|통과|미검증} {[대상: 지시|제안안] ← 지적일 때만}: {지적 또는 확인 근거 — 파일:줄/명령/함수명}
  - 실패 시나리오: {입력·상태} → {잘못된 결과}      ← 지적일 때만
  - 미검증: {확인 대상 · 시도와 결과 · 부족한 증거}  ← 확인 불가일 때만
- 문제 정의 — {판정}: {...}
- 대안 — {판정}: {...}
- 비용 — {판정}: {...}
- 실패 모드 — {판정}: {...}
- 되돌리기 — {판정}: {...}

### 종합
{`이의 없음` 또는 가장 심각한 지적 요약. 미검증 항목이 있으면 함께 명시}

## 3단계 — 메인 판정

1. 감사자의 모든 `BLOCK`을 보존하고 각각 `해결` / `기각` / `미해결`을 기록한다. 제안자가 다루지 않은 지적도 포함한다. `해결`에는 권장안에서 실패 경로를 제거한 근거, `기각`에는 직접 확인한 반증이 필요하다. 수정 예정이나 제안자의 침묵은 해결·기각 근거가 아니다. 대상 태그는 참고용이며 이 증거 요건을 대체하지 않는다.
2. `미검증` 항목은 확인 대상·시도와 결과·부족한 증거를 보존한다. 축 누락이나 근거 없는 `통과`도 `미검증`으로 처리한다. 확인된 `BLOCK`과 미검증 항목이 함께 있으면 둘 다 남긴다.
3. 근거가 있고 미해결 `BLOCK`·`미검증`·`[가정:공백]`에 영향받지 않는 합의 부분만 조용히 확정한다.
4. 메인이 확인할 수 있는 것은 직접 확인한다. 남은 `BLOCK`·`미검증`·`[가정:공백]` 중 사용자 판단이나 자료가 필요한 지점만 질문한다. Claude Code는 `AskUserQuestion`, Codex는 대화 응답을 사용한다.
5. 미해결 `BLOCK`이나 `미검증`이 하나라도 남으면 최종 확정과 검증 완료를 보류하고 사유·필요 증거를 출력한다. 남은 것이 없으면 불필요한 질문 없이 단일 권장안을 출력한다.
6. 감사자의 `WARN`과 `NOTE`는 권장안 아래에 목록으로 남긴다. 단, 실패 시나리오 없는 지적은 폐기한다. 이 필터로 `미검증`을 삭제하지 않는다.
7. 서브에이전트를 추가 호출하거나 `fight-clarify`를 자동 호출하지 않는다.

출력은 단일 권장안 하나다. 단, 확정 보류 시에는 보류 사유와 조건부 권장안을 구분한다. "둘 다 장단점이 있다"로 끝내지 마라.
